    The bug: a turn budget that does not bound a turn

    Found by a model too slow to hide it. With turn-deadline: PT120S a turn ran 24 minutes. The deadline is checked between model calls and around tool rounds — but Spring AI retries inside a single call, and nothing interrupts a blocking inference. FR-010 requires a turn bounded in elapsed time; it is bounded in rounds and only nominally in time, and SC-008's thirty seconds rests entirely on that difference. A fast provider would have hidden this until a slow day in production. It is T045, it needs no model, and it must land before any latency figure is trusted.

    The account setting: ADR-0026 condition 3

    The exception that lets the preview use an API rests on six conditions. Condition 1 — an allow-list of exactly one number — is enforced at startup: the application refuses to run otherwise, so admitting a second person needs an amendment rather than a property edit. Condition 2 is enforced in the tool surface. Condition 3 is not yet confirmed: no training on prompts, retention at the provider's minimum, a processing agreement. It must be settled before real birth details are sent, not after — which makes it the first thing to do, because every remaining task sends them.

    And one consequence worth planning for

    v3.0.0 added to Principle III that a correctness verdict is tied to the model that produced it. So the verdict earned on the API is the verdict for the API. Moving to a self-hosted model at public launch re-opens SC-001 rather than inheriting it — a scheduled cost, not a surprise, and the reason T044 exists.

    Five things only running the code could find

    Five analyze passes hardened the spec and the plan before a line was written, and two of them were load-bearing: the single-path ArchUnit rule as specified could not be implemented, and the turn record had no column for the question it exists to make reviewable. Then the code found four more that no amount of review would have:

    1. Every tool call silently did nothing. Spring AI binds @Tool arguments by parameter name, and @ToolParam has no name attribute — so without compiling with -parameters every argument arrives null. A tool asked for the disease table answered "no such table: " for an argument the model had supplied correctly. A real model would have looked merely stupid; the stub tier showed the cause.
    2. The application would not have started. EntitlementProperties carried @ConfigurationProperties and nothing registered it. A properties record is only a bean if something asks for it, and no unit test loads a context.
    3. The schema did not validate, and the seed command was dead code. A @Lob String with no length maps to TINYTEXT — 255 bytes — against a LONGTEXT column; had it matched, a turn's tool calls would have been truncated at 255 characters. And a nested @Configuration inside a @Component is not component-scanned, so the owner's birth-data seeder was never wired. Both surfaced the first time a container runtime was switched on — which also ran a golden-chart test that had been failing since SPEC-010, because the cache deliberately stopped stamping the chart's own engine version and nobody could see it without Docker.
    4. The turn budget does not bound a turn. With turn-deadline: PT120S, turns ran 24 minutes. The deadline is checked between model calls and around tool rounds — but Spring AI retries inside a single call, and nothing interrupts a blocking inference. FR-010 requires a turn bounded in elapsed time; it is bounded in rounds and only nominally in time, and SC-008's 30 seconds rests entirely on that difference. A warm Scout would have hidden this until a slow day in production. It is T045, and it is buildable without a GPU.
    5. A clamp that would have eaten the advisory sentence. The reply clamp read the sensitivity off the turn scope while the output stage decorated using the one the answerer returned. With a stub they diverge, the clamp failed to recognise the appended advisory, and trimmed away the one thing Constitution V makes obligatory. The handler now captures the answer at the boundary it passes through — and the contract says not to "simplify" that away, because the next reader would.

    The question that had been open for three days, and why the answer changed

    A second person's chart — the owner types a friend's birth details and asks about them (FR-011, US1 scenario 4) — was unavailable because no geocoder is wired. The framing was "defer it, or wire a geocoder". Both were incomplete. v3.0.0's exception forbids processing any other living person's data while a deployment uses a third-party API: the owner can consent for himself, never for a friend. So wiring a geocoder would have ended the permission rather than completing the requirement.

    It is resolved both ways: the requirement is scoped to self-hosted deployments (FR-011a), and the tool is gated on the provider so building the missing half cannot breach the condition by accident. It reports which of the two reasons applies, so "forbidden" stays distinguishable from "not built yet".
